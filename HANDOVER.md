# Handover — for the next coding agent

You are taking over sqlgami at `v0.1.0-rc1` to stress-test it and to carry the open list below.
This page is the map; the code and the tests are the territory. Everything measured here says
how it was measured. No employer, customer or product names appear in this repository; keep it so.

Standing constraints (the owner's, not negotiable): the repository is private — never change its
visibility, collaborators, secrets, Pages or webhooks; push only to the private origin at green
points; never commit credentials (`.env` holds `HF_TOKEN`; `git log --all -- .env` must stay
empty); Apache-2.0, no monetisation, no publishing anywhere; the only BigQuery project is the
sandbox `sqlgami-dev-1109` (enforced in code; §4); live `score()` stays deterministic, no model,
≤ 50 ms by default; models run offline only and only non-Chinese families (allow-list in
`sqlgami/contrib/hf.py`, Claude allowed); the term catalogue guesses nothing; bench content
(golds, catalogues, fixtures recipes) is the bench author's — propose, never edit; held-out sets
are opened once, scored once at a stated commit + bundle, reported unchanged (§3).

## 1. Architecture map

```
src/sqlgami/
  scorer.py        Scorer: loads catalogue/terms/bundle once per process; score()/explain()
  pipeline.py      the stages: parse → statement → schema → static → fixtures → dry_run → sample
                   → consistency → reconciliation → question; the deadline (_Deadline, RESERVE)
  analysis.py      parse, safety gate, script binding (DECLARE/SET), view/TVF expansion, qualify,
                   type annotation (the _Resolver)
  safety.py        what may be sent: function allow-lists per engine (_functions.py, generated by
                   tools/function_lists.py), refused built-ins, system tables, BigQuery namespaces,
                   policy opt-ins (wildcards, time travel, SESSION_USER), review of view bodies
  catalog.py       Catalog/Table/Column from DDL, a connection, or a dict; views, TVFs, scalar UDFs,
                   keys (incl. conditional keys), snapshot columns, required predicates
  model.py         SelectModel: sources, joins, bound constants, or-groups, key inference
  checks/          static checks: joins.py (fan-out, grain), aggregation.py, predicates.py
                   (checker-owned: do not edit without them), expressions.py, policy.py (or_chain)
  question.py      question-vs-SQL checks (top_n, output_columns, sorting, shape, …)
  terms.py         the term workbook: load/validate/match/pattern; named numeric slots; qualifiers
  termcheck.py     judging SQL against matched terms (filter/window/source/chain/rank, KPIs)
  bundle.py        compile_bundle (offline): fixtures, references' results, variants, manifest;
                   Bundle (load, stored_for, hash); _executable (slots, scripts, translation)
  fixtures.py / fixture_rules.py   synthetic fixtures; date_step/one_true/sequence/grid/derive
  translate.py     BigQuery → DuckDB: allow-list (CORE), constructs_of, map_tables, inline_functions,
                   _rewrite (the proven rewrites), column_types_of, unverified_in_text
  expand.py        offline expansion with a model (wordings and paraphrases, kept only if they
                   re-match deterministically)
  scoring.py       priors, weights, caps, calibration hook;  calibration.py  IsotonicCalibrator
  consistency.py / reconcile.py   live engines only: agreement between alternatives, anchors
  doctor.py / cli.py / templates/pilot   `sqlgami init|doctor|compile|score`
  engines/         duckdb, sqlite, postgres adapters (live path);  contrib/bigquery.py  the
                   OFFLINE sandbox adapter (dry run, native run, load, ledger);  contrib/hf.py
```

Bundle format (`bundle/`): `manifest.json` (dialect, `schema_hash`, `tables` map, `functions`,
`column_types`, `unique_keys`, `untranslatable_views`, fixtures with digests, `expansion`,
`references_with_free_numbers`), `references.json` (key, question, SQL, params, terms = the
question's pattern, slots, `slot_aliases`, stored results per fixture, `variant_of`),
`fixtures/<name>/*.csv`, `schema.sql`, `terms/` (the workbook copy), `review/` (expansion
proposals), `rejected.jsonl`. `Bundle.hash` is the content hash reported as
`signals.fixtures.bundle`. ADRs: `docs/adr/0001` (the term catalogue is host metadata),
`0002` (deterministic live scoring, models offline), `0003` (+ addenda: BigQuery through a
proof-gated translation; B4–B7; the red-team outcome).

## 2. Running things

- Tests: `.venv/bin/python -m pytest -p no:cacheprovider -q` (filter `nanobind`/`leaked` noise
  from DuckDB; `uv` is not installed, use the venv). Postgres tests need `SQLGAMI_TEST_PG_DSN`
  (a docker container `sqlgami-pg` on 127.0.0.1:5440). BigQuery native proofs need
  `SQLGAMI_BQ_LIVE=1 SQLGAMI_BQ_PROJECT=sqlgami-dev-1109` (`tests/test_bigquery_translation.py
  -k native`, `tests/test_bigquery_boundary.py`, the checker's `*_still_hold` tests).
- `tools/function_lists.py` regenerates `_functions.py` (needs the Postgres DSN).
- benchkit (`.venv/bin/python -m benchkit …`): `sync <shared> <copy>` (the ONLY way bench content
  enters the repo; md5-guarded, a stale copy refuses to load — `BENCHKIT_ALLOW_STALE=1` keeps
  frozen inputs for a recorded run), `build`, `validate`, `audit`, `compile <suite> --engine
  bigquery --from-seeds [--references file] [--expand hf:<model>]`, `evaluate <suite> --engine
  bigquery --mode static --candidates file [--bundle dir --terms-from-bundle] --run-id name`
  (labels from native BigQuery, cached per seed and statement under `bench/.runs/bigquery/cache`),
  `bq-native <suite> --seeds … [--no-load]` (native golds/bugs vs DuckDB golds vs the
  translation; the agreement metric), `latency`, `calibrate`, `label`.
- Scratch scripts used for the recorded numbers live in the session scratchpad, not the repo;
  the recorded runs are under `bench/.runs/` (eval JSON per run id).

## 4. The sandbox rules

`sqlgami-dev-1109` only (billing disabled, free quota). `contrib/bigquery.sandbox_project()`
refuses any other project before a client is built; `SQLGAMI_BQ_PROJECT` must be set for bench
commands. ADC only, no key files. Datasets: `bench_hr_snapshot_s<seed>_hr[_ref]` (the bench
seeds, 60-day expiry), `bench_translation` (fidelity fixtures), the checker's `bench_checker_*`;
every create/load/delete is appended to `bench/.runs/bigquery/datasets.jsonl` — that file is the
cleanup list. Nothing that can bill; queries stay within the free tier (the sandbox adapter
refuses a statement over a bytes limit). `score()` never touches BigQuery.

## 6. Open work, in priority order

- **H1 — two-tier API.** `score(…, deadline_ms=50)` returning "evidence: static only" /
  "fixtures: k of n", plus `score_complete` (a continuation that finishes the fixtures off the
  request path), cached per (sql hash, bundle hash); measure warm-vs-cold fixture share on the
  w4/w4v2 BigQuery golds; profile sqlglot parse caching (parse alone is 17–26 ms on 60–80-line
  scripts). This is what made a correct query score 0.51 at 50 ms in the owner's demo.
- **H2 — static ceiling.** Correct statements plateau at ~0.54–0.59 without a fixture verdict
  (`scoring.PRIOR["static"] = 0.62` minus notes). Measured: LOW notes inform-only lifts the
  correct median 0.811 → 0.819 but lowers AUROC 0.944 → 0.938 on the 168 dev candidates, so
  they kept their weight; look for a principled lift (e.g. term outcomes all satisfied as
  positive evidence) and measure it the same way (`scratchpad/ceiling.py` method: static mode,
  frozen w4 bundle, labelled dev candidates, median/AUROC/≤0.4/≥0.8).
- **H3 — paraphrase variants of templated references.** `expand` paraphrases fail to re-match a
  reference whose question has `{slot}` tokens (they enter `Catalogue.pattern()` as identifier
  tokens); fix in `terms.pattern`/`bundle._accept_expansion`; then recompile the w5 bundle.
- **H4 — slot binding, second round.** Aliases by role are in (`Reference.slot_aliases`); still
  open: a term phrase binding two slots of the same notion in one question; `{m}`-style ranges
  with named slots; the author's note that "most recent {n_months}" wordings collide across
  terms (longest phrase wins the span — document or add term priority).
- **H5 — TVF support on a production library.** Read/expand/run is built and tested on
  synthetic DDL and the sandbox's TVFs; w6/w6v are the honest test (held out). Known gaps:
  TVF bodies with unverified constructs make every reader `not_run`; recursion/nesting limit
  32; JavaScript UDFs `not_run`.
- **H6 — allow-list growth, by proof only:** `DATETIME_DIFF`, `TIMESTAMP_ADD/SUB/DIFF`, `JSON_*`,
  `TO_JSON_STRING`, `ISOWEEK`, `ARRAY_AGG … IGNORE NULLS` (a FILTER rewrite), `ARRAY_AGG … LIMIT`,
  `FORMAT_TIMESTAMP`. Each needs native boundary cases in `tests/test_bigquery_boundary.py` first.
- **H7 — new term kinds** the bench author proposed (`projection`, `decomposition`, `measure`,
  `rank_column`, `anchor_choice`, `date_trunc_source`, `grid_filter`): documentation-only today.
  What could be checked deterministically: `projection` (ARRAY_AGG … ORDER BY … LIMIT n — once
  the construct is verified, the fixtures decide; statically: the ORDER BY direction and the
  cap), `rank_column` (a column that must be a ranking function over a stated partition —
  checkable like `rank`), `date_trunc_source` (which column a month bucket is taken from —
  checkable like `source`), `grid_filter` (a required filter on the grid — like `filter`).
  Stay documentation-only: `measure` (share of total, tenure in ISO weeks — fixtures judge it),
  `decomposition` (UNNEST of chain levels — the or_chain policy already accepts the pivot),
  `anchor_choice` (a conditional fallback — control flow the live path does not run).
- **H8 — static misses** (the 30 `test_known_miss` cases): outer-join nullification through
  CTEs/derived tables/EXISTS/COALESCE/HAVING; soft-delete flags computed but never filtered.
- **H9 — B5 native fixture mode** (load the bundle's fixtures into `bench_fx_<hash>_*`, run
  candidate and reference natively with the same verdict logic, disagreement fails CI) and
  **B6** (seeded differential fuzzing over the allow-list; the 145 + 79 boundary cases are the
  seeds; the native job is `SQLGAMI_BQ_LIVE=1`).
- **H10 — Postgres** as a second production engine (adapter exists; w4v2 dev scoring paused).
- **H11 — calibration** shipped with the pilot's labels (`IsotonicCalibrator`).
- **H13 — fixture "match" on candidates the native label calls wrong** (w5v q031v1-a/b and
  q032v1-b: 10 cases, 4 ≥ 0.8 — false confidence, the worst failure mode). The variant and base
  ask the same output, so the match key is not the cause. Compare, from the native cache, the
  candidate's rows with the base gold's and the variant gold's on the same seed: if candidate =
  base gold ≠ variant gold, the variant gold differs and the reference is the wrong one; if
  candidate ≠ base gold natively but = on the fixtures, the fixtures lack the separating rows
  (then B5 native fixtures, or a fixture rule for that case). First thing to do after the tag.
- **H14 — `term_missing` false alarm when a filter term is applied in a subquery scope** (w5v
  q029v1-a/b golds: `active` applied inside the segment subquery; the judge looks for it on the
  fact's own scope).
- **H15 — control-flow scripts** (`IF`/`WHILE` with `SET`): the live path does not run them
  (`multiple_statements`, 0.05); w5v q032 variants are such scripts. A bounded interpreter for
  `IF NOT EXISTS (...) THEN SET` fallbacks would cover the owner's idiom.
- **H16 — native labels for TVF/view sets.** `benchkit` loads the bench seed datasets with
  tables only; the w6 schema's TVFs, views and UDF are not created in the sandbox, so every w6v
  gold and 143/152 candidates fail natively and no label is valid. Create the routine and view
  DDL in each `bench_hr_snapshot_s<seed>_hr` dataset (`load_seed`, sandbox only, `bench_`
  prefix, recorded in the ledger), then score w6v once at `438710c` + `dfb5c050…` without
  touching the code first. The fixture verdicts of the unmeasured run are in
  `bench/.runs/w6v-bq-b/`.
- **H12 — docs/packaging**: `sqlgami init|doctor` accepting an INFORMATION_SCHEMA JSON/JSONL
  dump directly; wheel verified in a fresh venv at 0.1.0.

Checker-owned files: `checks/predicates.py`, `checks/aggregation.py` — coordinate before editing.

### 7.1 w5v (recorded once; the honest BigQuery figure of this release)

Caveats first: five of the eleven w5 references compiled (q030, q031, q032-eq, q035, q035-eq);
q029/q029-eq/q032 (`ARRAY_AGG … IGNORE NULLS`), q033 (`ARRAY_AGG … LIMIT`) and q034/q034-eq
(`ISOWEEK`) were rejected as unverified; no paraphrase variants compiled (H3). Questions
`07d30c9d…`, candidates `362f92fa…` (168: two Claude models plain + style, Llama 8B/70B, Gemma,
Phi-4), catalogue Terms `ddbfb833…`, glossary `130b3045…`.

**w5v (21 variants, 168 candidates: 33 correct, 135 wrong; the 42 style-rewritten candidates
were all wrong natively; bundle `601bedb8…`).** **First contact at `aa9b2ad`** (the code before three defects this set revealed were fixed;
reproduced exactly, deterministic, cached labels): AUROC 0.818 without the bundle (plain
0.820), 0.800 with it unlimited, 0.814 at 50 ms; correct ≤ 0.4: 5/33; wrong ≤ 0.4: 66/135;
wrong ≥ 0.8: 0/135 without the bundle, 4/135 with it. **After fixes found on this set, at
`438710c`:** AUROC 0.863 / 0.842 / 0.859; correct ≤ 0.4: 2/33; the rest unchanged. The
first-contact number is the one to cite as honest; the second is tuned on this set.
Wrong ≥ 0.8 with the bundle: fixture "match" verdicts on wrong candidates for q031v1-a/b and
q032v1-b (10 such matches in all, 4 above 0.8). The variant and its base reference ask the
same output (identical column lists), so the cause is not the match key: either the synthetic
fixtures lack the rows that would separate the candidate from the gold, or the variant gold
differs natively from the base gold the reference was compiled from. Not established; the
cached native rows can settle it (H13). This is the worst failure mode — false confidence —
and it is open in this release.
Fixture stage: 14 match, 4 mismatch, 22 "no reference for these values" (a bare "1" in the
question no term binds), 73 "no reference matches this question", 43 "cannot run" (the q032
variants are `IF`-control-flow scripts the live path does not run; 3 candidates do not parse).

carry a `term_missing` HIGH where the `active` filter is applied in a subquery scope — a false

bundle at 50 ms: p50 27 / p90 53 / p99 70 ms, 18/168 cut by the deadline; without it p50 21 /

bucketing, ARRAY_AGG projections, pivots) and six of its eleven base references could not
compile (L2), so most candidates had no fixture to be judged on.

The three defects the first contact revealed and `438710c` fixed: the new `access_filter_value`
check read a `flag = 1 OR flag = 1` group as the chain's value (3 false alarms); positional
STRUCT pivots and chain comparisons inside OR-branch conjunctions were not recognised (the q031
variant golds scored 0.09). Cite the first-contact number; the second is tuned on this set.
