Is the SQL your AI just wrote actually correct?

sqlgami answers that question. Our mission: make SQL written by LLMs and coding agents safe to trust in production. sqlgami checks every query the way a careful analyst would, against your schema, your business definitions and verified reference answers, and returns a deterministic confidence score with the evidence, in milliseconds. No AI judge, no guesswork, and nothing leaves your systems.

Wrong SQL doesn't crash. It returns a believable number.

-- "active headcount, last 8 pay periods"
SELECT p.period_seq,
       COUNT(DISTINCT e.assoc_id) AS active_n
FROM   pay_period_dim p
JOIN   emp_period_snapshot e
  ON   e.period_end_dt = p.ppe_dt
WHERE  p.period_seq BETWEEN -8 AND -1
  -- correct: BETWEEN -7 AND 0
  AND  e.status_cd = 'A'
GROUP  BY 1

In our tests the open models we could call cheaply were right 0–29% of the time on hard questions, so a judge built from them would be unreliable, and a strong judge adds latency and cost to every query.

Four layers of evidence, no AI in the loop.

Layer 1

Safety & schema

Checked against the real tables, views and table functions. Anything unsafe is refused.

Layer 2

Rule checks

About 40 known failure patterns: join fan-out, NULL traps, wrong grain, missing scope.

Layer 3

Our definitions

"Active", "last N pay periods", "my organisation": checked against what the SQL does.

Layer 4

Check the answer

Run the query on small mock datasets built to expose mistakes, and compare its answer with a verified reference query. This catches errors no rule can see.

Same SQL, same score, every time. Runs inside the application in about 50 ms.

Architecture

Inside the answer check

Recognise

Match the question's phrases to your defined terms: "last 13 pay periods", "my organisation".

Bind values

Pull out the numbers and parameters: n = 13, manager = 52002. Never guessed: an unbound number means "can't check".

Find the reference

Look up the verified query registered for that pattern, written as a template.

Run both

Execute the reference and the candidate on 6–7 small mock datasets, each under the same values.

Compare

Fingerprint both results. Any difference on any dataset is a high-severity finding, with the rows as evidence.

Report

Verdict, score and range, findings in plain English, and which checks ran or were skipped.

The mock datasets are deliberately awkward: ties at a rank boundary, NULL statuses, restated snapshot rows, empty periods, people reachable only through the functional chain, segments that vanish. Six small datasets exposed all 41 planted mistakes in our HR suite; each query runs in about 5 ms on them.

BigQuery fidelity, proven against BigQuery itself

How it works

Live scoring never calls BigQuery. Candidate SQL is translated to an embedded engine through an allow-list in which every construct has passing cases run on real BigQuery: dates and weeks, COUNTIF, SAFE_DIVIDE, QUALIFY, UNNEST, NUMERIC, LIKE, DECLARE/SET scripts.

Anything outside the list returns "can't check", never a verdict.

What we checked

  • 770 / 770 expected-answer runs identical natively and translated, on 11 datasets
  • 0 value disagreements across ~490 comparisons of 224 real LLM queries
  • 40 defects found by an independent red team (unsafe system-table reads, week boundaries, offsets, division by zero), all fixed and turned into tests
  • 4 inherent engine differences documented, not hidden

How we kept the numbers honest

Test data

  • Production-shaped HR snapshot schema with views and table functions; 11 seeded datasets, half deliberately nasty
  • Expected answers written by one agent, then re-derived blind by an independent auditor and compared on every dataset. This caught more than a dozen wrong expected answers before any scoring
  • Candidate SQL written blind by 6 models, frontier and open

Scoring discipline

  • Each test set is hidden from the builder until scored, and scored once
  • The reference bundle is frozen and fingerprinted before release
  • Right and wrong labels come from execution, on BigQuery for BigQuery tests
  • Any set used for fixes becomes tuning data; only untouched sets are reported as results

What a team prepares

1

Export schema

Data engineer

One DDL export of tables, views and table functions from INFORMATION_SCHEMA.

2

Define terms

Business + data engineer

An Excel sheet of terms and KPIs: the words people use, and what they mean in data.

3

Write references

Analyst

One verified query per recurring question pattern. Start with the top 10–20.

4

Declare data rules

Data engineer

A few lines describing realistic data. Mock data comes from these; no production rows leave.

5

Compile

Automated

References verified, mock data built, one versioned bundle kept in git.

An undefined term lowers the confidence. The system never guesses what a term means.

What integration looks like

from sqlgami import Scorer

scorer = Scorer("bigquery",
    catalog=open("schema.sql").read(),
    terms="metadata/terms.xlsx",
    bundle="bundle/")

report = scorer.score(sql, question,
    params={"manager_id": 12003})

report.verdict        # likely_right
report.confidence     # 0.81 (0.69–0.93)
report.findings       # plain-English list
report.timing         # ms per stage

Operating model

  • A Python library inside the agent or app: no service, no network call
  • The bundle is a versioned folder in git, rebuilt by CI when terms or references change
  • Shadow mode first: log scores, block nothing
  • Then gate: route below-threshold queries to a person

What it guarantees, and what it doesn't

Guaranteed

  • Deterministic, with no AI at scoring time
  • Unsafe SQL is never run
  • Unsupported SQL says "can't check", never a guess

Depends on preparation

  • The answer check needs a reference for that question pattern
  • Undefined terms reduce confidence
  • Mock data is only as good as its rules

Still maturing

  • 70+ line scripts may get rules only within 50 ms
  • Rare false confidence: a few wrong answers still score above 0.8
  • Score calibration on our data

Risks and next steps

Next

  • Fix the rare false-confidence cases (H13)
  • Two-step scoring with caching for long scripts
  • Score calibration on real-world data

Risks

  • Coverage depends on how many question patterns get references
  • Unusual phrasing may not match a defined term
  • Our tests are synthetic; real-world use is the real test

Mitigations

  • Start with the top 10–20 patterns; expand from usage logs
  • Offline phrase suggestions, reviewed by the team
  • Run in shadow mode until the numbers hold on your data
